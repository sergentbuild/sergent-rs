# Terminology

For anyone implementing the Sergent Specification, respect these terms as the stable vocabulary of
Sergent. They are not loose labels; every definition below is normative. The entries appear in
alphabetical order, and each entry stands on its own for a first-time reader.

## admissibility pass

**admissibility pass**: one ordered traversal of the candidate Operations of an Execution Plan, in
which the runtime checks each Operation's [Operation Admissibility](#operation-admissibility)
against one fixed Scene snapshot, the validated Intent, and the selected Target, and stops at the
first rejection. The initial pass runs against the Run's base Scene. A second pass runs only when
shared live state rebases a stale Patch onto a changed Scene. The
[execution model](./execution-model.md#operation-admissibility-flow) defines the pass rules.

## agentic layer

**agentic layer**: the middle layer of a Sergentic application: the copilot that observes the
user's work and data, then uses the model to propose actions in terms of the Programming
Interface. It expresses the execution flow with ordinary software control structures and the
decision-making process with the Recipe. The
[framework specification](./framework.md#sergent-vision) defines the three layers.

## algorithmic layer

**algorithmic layer**: the bottom layer of a Sergentic application: deterministic code that
manages the domain data and offers the Programming Interface to the agentic layer. It may be an
existing software system. Everything it exposes to the agentic layer must be deterministic.

## Execution Plan

**Execution Plan**: (also spelled "ExecutionPlan" if used in programming context as the name
of the Execution Plan object) a typed object (analogy to a small programming script). On
the type level, the Recipe appoints it; during a Run, the runtime derives it from the
Plan Proposal through the Recipe's rule, after a validated **Continue** Intent. It is made of
Operation objects over the Programming Interface.

## Intent

**Intent**: a typed statement of what the Sergent Instance wants to do. A validated
Intent also determines the next control decision: **Continue** to the **Execution Plan**
phase, or successfully **Stop** when no mutation is needed.

## Intent Proposal

**Intent Proposal**: the typed input from which the runtime derives the Intent through the
Recipe's rule. In a model-backed Intent phase, it holds the output generated by the model.
The application defines the domain-specific proposal types used for model output. A runtime
implementation may define generic proposal variants for deterministic Intent modes such as
[pass-through](#pass-through).

## MindBuf

**MindBuf**: the required observation input for each Run. It typically carries recent
information the committed Scene cannot hold: the user's recent actions, outcomes of earlier Runs, and
non-blocking errors or rejected attempts. The application curates and compresses this information,
then renders it as context-ready text for the model. It carries facts only, never control.

## Observation

**Observation**: the two channels given to a Run: the [Scene](#scene) and the **MindBuf**. Do not confuse
the MindBuf with control, such as the Run Kind and the Target selection policy. The application
configures such control before the Run; the MindBuf never carries control.

## Operation

**Operation**: one typed call via the algorithmic layer's **Programming
Interface**. It is the model-visible building block of an Execution Plan. An
Operation never stands on its own; it exists only inside an Execution Plan,
similar to how a statement exists only inside a programming script.

## Operation Admissibility

**Operation Admissibility**: the application-defined decision whether one typed Operation is
compatible with the Scene, the validated Intent, and the selected Target. The
[execution model](./execution-model.md#operation-admissibility-flow) describes the complete rules.

## Operation Registry

**Operation Registry**: the closed set of Operation definitions that the
application makes available to a Run that can reach the Execution Plan phase.
It is the source for canonical schema branches, typed Operation decoding, and
the Plan Proposal envelope. Its absence declares an Intent-Only Recipe. Its purpose is similar
to the grammar in a scripting language: what statements exist.

## pass-through

**pass-through**: the runtime-provided deterministic Intent Proposal variant. When the application
configures an Execution-Plan-Only Run, the runtime supplies this variant without a model call.
The runtime still derives the Intent through the Recipe and validates it. Pass-through
is intended to fast-forward to model-backed Execution Planning. A **Stop** Intent is technically
possible but offers no practical value. Pass-through has no Intent Proposal request or schema;
it is neither model output nor the derived Intent.

## Patch

**Patch**: an ordered, replayable sequence of Operations that the runtime compiles from a
validated Execution Plan, dry-runs in isolation, and then commits in that order. Patch
Operations are isolated copies of the Execution Plan's Operations. They retain
the same framework-defined Operation IDs for trace matching.

## Plan Proposal

**Plan Proposal**: the typed Operation data the model proposes after a
**Continue** Intent. Like every proposal, it is derivation input with no
mutation authority; the runtime derives the Execution Plan from it.

## Programming Interface

**Programming Interface**: the structured definition of all the Operations
the algorithmic layer offers to the agentic layer. It works like a
scripting binding for a closed software system: selective, controlled, and
task-driven. Note, Programming Interface is a formal concept, not a required
object or interface. An implementation can use its language-specific features
such as file scope, module, or package to materialize this formal concept.

## Proposal Schema

**Proposal Schema**: the canonical structural representation carried by a
model-backed request, named `Proposal Schema`. It derives from the exact
typed Intent Proposal or Plan Proposal definitions used at the model-output
boundary. It constrains provider generation but never replaces that typed
crossing. Its purpose is to utilize the frontier LLM's output schema control feature
to output schema-conforming data.

## Recipe

**Recipe**: the application-defined agentic policy object for a [Run](#run). It connects the
application's [Intent Proposal](#intent-proposal) and [Intent](#intent) types with the
[Operation Registry](#operation-registry), the registered Operations from which the runtime builds
the Execution Plan. During a Run, it builds a model request for each model-backed proposal phase
that the Run reaches: the Intent request and the Execution Plan request. Pass-through has no
Intent Proposal request or schema. The Recipe supplies the rules that derive the
typed Intent and Execution Plan values, enforces application semantic rules, and compiles a Patch.
It also declares the no-target error that the runtime returns when Target selection finds nothing.
It is the brain of the Sergent Instance. Since the Recipe is an object, an implementation can
supply mechanical defaults for the Recipe tasks that the framework rules allow, and a
runtime-provided deterministic Intent Proposal variant such as pass-through.

## Run

**Run**: one bounded invocation of the configured Sergent Instance, also called a Sergent Run. It
receives one Observation, performs one Target selection, generates at most two proposals, and may
commit at most one change. The [execution model](./execution-model.md) defines its ordered flow
and terminal behavior.

## Run ID

**Run ID**: the stable identifier that the framework defines for one Run.

## Run Kind

**Run Kind**: the application-configured choice of which proposal phases a Run uses: both phases
(a model-backed Intent and a model-backed Execution Plan), Intent-Only (a model-backed Intent that
may only **Stop**, because the Recipe has no Operation Registry), or Execution-Plan-Only (a
pass-through Intent and a model-backed Execution Plan). The Run Kind is control that the
application configures before the Run; the MindBuf never carries it.

## Run Record

**Run Record**: (also spelled "RunRecord" if used in programming context as the name
of the Run Record object) the framework's authoritative evidence of one Run. As a concept,
it covers the data structure, the tooling, and the processes that curate the Run's
activities. As a programming term, it is the framework-defined data structure that
carries the Run identity, timing, Scene transition, outcome, and cancellation facts,
together with one sequence field: the Run Record Ledger. The structure is the same in every
implementation; only the captured values inside it are implementation-native. It is inert data.
Persistence policy remains separate from it.

## Run Record file

**Run Record file**: the JSON Lines file that the opt-in Run Record harness writes. It
persists each complete Run Record inside a Run end record, beside the framework Run start
records and any application and user events. The
[Run Record file format](./run-record-file-format.md) defines it.

## Run Record harness

**Run Record harness**: the opt-in, runtime-provided tooling that writes Run Record files. It
persists the framework Run boundaries (a Run start carrying the `started` progress snapshot and a
Run end carrying the complete Run Record) and the application and user events that the
application records. The application chooses the log directory, the log identity, retention,
redaction, and access.

## Run Record Ledger

**Run Record Ledger**: the sequence subfield of the Run Record, similar to a dynamic array,
whose elements are **Step Records** in execution order. One Step Record captures one
started step of the Run, including any model call nested inside that step. The word
"ledger" is an analogy, like "script" for the Execution Plan: the runtime appends to this
sequence and never deletes or mutates an element, so the Run Record holds faithful data. It
does not prescribe a financial-ledger data model. Use "Ledger" only in this programming
context; the Run Record as a whole is never called a ledger.

## Scene

**Scene**: the application-tailored data model and the bounded state the agent may observe. The
deterministic runtime may modify a Scene only through the commit process using a validated Patch.
The business state object and the runtime-facing Scene objects may be the same or separate objects
due to protection/abstraction layering.

## Scene Actions

**Scene Actions**: the deterministic Scene capabilities the runtime requires: identity, isolated
clone, Target selection & existence check, Target-aware apply, and verification. It is also known
as the Scene API. The Scene Actions power the Operations and Execution Plan.

## Sergent

**Sergent**: a technical concept and vision for building and operating agentic applications. The
Sergent Specification records that concept and vision as a rulebook, and the
[Sergent Vision](#sergent-vision) names its central design choice.

## Sergent Instance

**Sergent Instance**: an object created from the language-specific Sergent implementation that
represents the Sergent Runtime. The application configures it with its Recipe and its Scene Actions,
then starts Runs on it, choosing the model for each Run.

## Sergent Result

**Sergent Result**: the terminal in-process return from one Run, carrying the final Scene, the
closed Run Record, the last reached stage, the terminal message and metadata, and the contained
observer delivery errors. The
[Run Record specification](./run-record-spec.md#the-sergent-result-structure) defines its exact
structure.

## Sergent Runtime

**Sergent Runtime**: the runtime that a Sergent Instance represents: the deterministic engine that
performs a Run, from Target selection through proposal decoding, Intent and Execution Plan
derivation and validation through the Recipe, Patch compilation, dry-run, and commit, to the
closed Run Record. These documents write "the runtime" as its short form.

## Sergent Vision

**Sergent Vision**: the design vision at the center of the Sergent Specification: build an
agentic application as three layers (the user behavior layer, the agentic layer, and the
algorithmic layer), let the model only propose, and let the deterministic Sergent Runtime derive,
validate, rehearse, and commit each change. The
[framework specification](./framework.md#sergent-vision) defines it.

## Sergentic

**Sergentic**: describes an application or software architecture built with the Sergent Runtime.
A Sergentic application separates the user behavior layer, the agentic layer, and the
algorithmic layer, as the Sergent Vision prescribes.

## Step Record

**Step Record**: one element of the Run Record Ledger: the evidence of one started step of the
Run, carrying the step's name, status, timing, input, output, error, and any model call record
nested inside that step. The [Run Record specification](./run-record-spec.md) defines the five
step names and the evidence each step records.

## Target

**Target**: the bounded Scene portion one Run may affect. It is the sole source of the
selected Target identity and Target-specific execution context. Common patterns include
a Target covering the whole Scene, a latest-item Target selected at Run start, an item collection Target selected
by id(s), and a mode Target that carries mode data defined and controlled by the application beside
the Target id. These patterns do not require a particular Scene shape.

## user behavior layer

**user behavior layer**: the top layer of a Sergentic application: the user interface and
application logic through which the user completes concrete tasks and sets the direction.

## Verification Report

**Verification Report**: (also spelled "VerificationReport" if used in programming context as
the name of the Verification Report object) the machine-readable result that the
application-defined Scene verification returns after the dry-run has applied the Patch to the
isolated Scene copy. It lists the domain-invariant issues found in the resulting Scene. An empty list
accepts the resulting Scene; any issue fails the dry-run, and the Run error carries the issues as
`verification_issues`.

## writer model

**writer model**: the application's answer to the question "who can write?": one serial writer,
turn-based writers, concurrent writers over disjoint data, or concurrent writers over shared data.
Serial writers serialize whole Runs, one Run per writer turn; other writes to the same authority
are excluded from Observation through commit. Overlapping Runs are concurrent even when their
commit writes are serialized. For concurrent Runs sharing one Scene, the application chooses
strict stale rejection or application-defined deterministic rebase. The writer model determines
the available commit policies (serial, divided authority, or strict rejection or rebase)
and is separate from revision representation. The
[framework specification](./framework.md#writer-model-and-revision-policy) defines the writer
model table.
